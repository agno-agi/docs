The Demo OS `taskboard` module registers an agent named **Planner** with the ID `planner`.

```python
from agno.agent import Agent

taskboard = Agent(
    id="planner",
    name="Planner",
    model=MODEL,
    db=agent_db,
    tools=[
        add_task,
        update_task_status,
        remove_task,
        list_tasks,
        agenda,
        plan_my_day,
        get_summary,
    ],
    session_state={
        "tasks": [],
        "categories": ["general", "work", "personal"],
    },
    enable_agentic_state=True,
    add_session_state_to_context=True,
)
```

| Setting | Behavior |
|---------|----------|
| `session_state={...}` | Supplies the initial state for a new session. |
| `enable_agentic_state=True` | Adds the `update_session_state` tool. |
| `add_session_state_to_context=True` | Adds the current state to the model context. |
| `db=agent_db` | Persists the session and its state. |

## Update state in a tool

Planner's custom tools receive a `RunContext`. They read and mutate `run_context.session_state` directly.

```python
from agno.run import RunContext
from agno.tools import tool


@tool
def add_task(
    run_context: RunContext,
    title: str,
    priority: str = "medium",
    category: str = "general",
    effort: str = "medium",
    due_date: str = "",
) -> str:
    state = _state(run_context)
    tasks = state["tasks"]
    task_id = f"T-{len(tasks) + 1:03d}"
    tasks.append(
        {
            "id": task_id,
            "title": title,
            "priority": priority,
            "category": category,
            "effort": effort,
            "status": "todo",
            "due_date": due_date,
            "blocked_reason": "",
        }
    )
    return f"Added {task_id}: {title}"
```

The live state mutation is included when the run's session is persisted. Passing a plain `session_state` argument to the tool would not match this implementation.

## Task model

| Field | Values used by Planner |
|-------|------------------------|
| `id` | `T-001`, `T-002`, and subsequent sequence values |
| `priority` | `high`, `medium`, `low` |
| `effort` | `quick`, `medium`, `deep` |
| `category` | `general`, `work`, `personal` by default |
| `status` | `todo`, `in_progress`, `blocked`, `waiting`, `done`, `cancelled` |
| `due_date` | `YYYY-MM-DD` or an empty string |

`agenda` selects overdue and due-today work. `plan_my_day` ranks actionable tasks by priority, due date, and effort.

## Session state and memory

| Data | Scope | Planner example |
|------|-------|-----------------|
| Session state | One session | The tasks currently tracked in that Planner session |
| Memory | A user across sessions | Work preferences and recurring planning patterns |
| Run context | One run | The live state and request context passed to tools |

Reopen the same session ID to continue with its state. Start a new session for a separate taskboard. Planner also enables agentic memory and past-session search for information that should carry across sessions.

## Try it

```text
@Planner add a work task to review the Q2 roadmap, due 2026-07-24
@Planner add a personal task to book a dentist appointment
@Planner show my agenda
@Planner mark T-001 as in_progress
@Planner plan my day
```
