Dash is a coordinate-mode team with an Analyst for queries and an Engineer for data assets.

```python
from agno.team import Team, TeamMode

dash = Team(
    id="dash",
    name="Dash",
    mode=TeamMode.coordinate,
    model=MODEL,
    members=[analyst, engineer],
    db=agent_db,
    learning=dash_learning,
    add_learnings_to_context=True,
    share_member_interactions=True,
)
```

The leader has no SQL tools. Its `db=agent_db` setting persists team sessions.
It delegates database work to one or both specialists and synthesizes their
responses.

## Member responsibilities

| Member | Intended work | Database connection |
|--------|---------------|---------------------|
| **Analyst** | Read data, write and validate queries, interpret results | PostgreSQL connection with `default_transaction_read_only=on` |
| **Engineer** | Create views, summary tables, and other assets in `dash` | Read-write connection with `search_path=dash,public` |
| **Leader** | Select members and combine results | No SQL tool access; the team database persists sessions |

Both specialists receive `search_knowledge_base`, schema introspection, SQL, and reasoning tools. The Analyst can also save validated queries. The Engineer can update the knowledge base after schema work.

## Access controls

The Analyst's connection sets PostgreSQL transactions to read-only. PostgreSQL rejects DML and DDL on that connection.

The Engineer uses a different control. A SQLAlchemy event listener searches statements for explicit writes to `public.*` and raises an error when it recognizes one. This regular-expression guard is best-effort. It can miss alternate SQL forms or unqualified targets, so it does not provide a database-enforced security boundary.

For a hard Engineer boundary, use PostgreSQL roles and grants that permit reads from `public` and writes only to `dash`.

## Query flow

For a direct data question, the expected flow is:

1. The leader delegates the question to the Analyst.
2. The Analyst searches knowledge for table metadata, query patterns, and business rules.
3. The Analyst executes SQL through the read-only connection.
4. The leader turns the member response into the final answer.

For work that needs a reusable view, the leader can involve both members:

1. The Analyst identifies the repeated query or missing data asset.
2. The Engineer inspects the schema and creates an asset under `dash`.
3. The Engineer records that asset in knowledge.
4. The Analyst queries the new asset through its read-only connection.

`TeamMode.coordinate` allows the leader to call multiple members. It does not restrict a run to one specialist.

## Knowledge and learnings

Dash separates curated material from model-selected learnings:

| Store | Contents | Use |
|-------|----------|-----|
| `dash_knowledge` | Table metadata, validated queries, business rules, Engineer updates | Exposed to Analyst and Engineer through `search_knowledge_base` |
| `dash_learnings` | Error patterns, corrections, and reusable observations | Attached through an agentic `LearningMachine` |

Knowledge search and learning writes are model-driven tool calls. The instructions request them, but the runtime does not guarantee that every successful fix is saved or reused.
